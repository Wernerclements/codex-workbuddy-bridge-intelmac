## 目标和架构

首个可用版本 v0.1：Codex 分配一个新任务，WorkBuddy 执行，Codex 收到文本结果和文件清单；能够查询状态、等待和取消。任务复用桌面应用的登录状态。暖启动路径 2.26 积分与新冷启动路径七条 2.88 积分已由用户用量页分别核对，其他已接受请求的消耗未知。

```mermaid

  A[Codex.app] -->|MCP 工具| B[本地桥接服务]
  S[可选 Skill 使用说明] -.-> A
  B --> C[macOS 实例发现与版本适配]
  C -->|已运行通道或原生受保护字段握手| D[WorkBuddy 桌面应用]
  D -->|应用内置运行时与本机 ACP| E[本项目自有 worker]
  E --> G[现有受保护登录配置]
```

首版优先使用 MCP 标准输入输出，由 Codex 管理服务进程；不另开对外 HTTP 端口。持续运行与登录启动可在需要时增加。具体 Codex 配置必须在实现阶段按照本机版本核验。

## 1 · 打通单个任务

1. 实现 macOS 实例发现：验证进程归属、用户归属和 socket；不能依赖 Windows PID 文件。
2. 独立 WorkBuddy 适配模块：协议能力探测、认证、端口就绪握手、任务创建和消息收集。
3. 为桥接器新建自己的 worker；复用桌面登录状态。避免直接接管用户正在使用的会话。
4. MCP 提供 `start_task`、`get_task`、`wait_task`、`cancel_task`、`get_result`、`health` 及 `respond_permission` 七个入口。
5. 使用 WorkBuddy 自己的会话注册渠道；未找到可靠渠道时，先不写桌面历史数据库。

验收：Codex 发起小任务，WorkBuddy 可观察到执行，返回结果正文与任务 ID；核对任务所用账号及应用用量。明确验证是否依赖额外模型 API。

## 2 · 补齐生命周期

- 自有持久化记录保存状态、事件和结果位置，凭证只保存在内存。冷启动使用私有临时 socket 和应用现有密钥辅助函数，不关闭静态加密、不生成新账号密钥。
- 状态至少区分等待、执行、等待用户授权、成功、失败、取消和结果不确定。
- 超时只结束等待，不自动重复提交任务；断线或服务重启先查询再决定恢复。
- 授权请求传回 Codex/用户，不照搬上游默认全权限和永久允许。
- 清理时校验实例与 worker 身份，只停止本项目创建的任务。持久化 `cleanup_pending` / `cleanup_confirmed`；服务重启继续清理未确认资源，不重新发送 prompt，也不改变已保存的终态。
- 结果包含文件路径和完成状态；长文本落盘，MCP 返回摘要和位置。

验收矩阵：成功、失败、取消、超时、权限请求、WorkBuddy 退出、桥接器重启、失效凭证、其他用户 socket、不兼容协议、文件结果。每项记录实际结果，不以模拟测试代替真实测试。

## 3 · 安装和发布

- 一份中文安装说明、一个安装入口、一个可选 Skill。
- 安装前检查 x86_64、Python、应用位置和版本。评估打包 Intel 运行时以避免用户编译依赖。
- 配置变更前备份，支持卸载与回滚；安装不能覆盖用户现有 MCP 配置。
- 完成本机端到端验收后再发布 `v0.1.0`，发布说明写明已验证的应用版本。

## 4 · 更新维护

每次 WorkBuddy 更新：先只读诊断，再运行单元测试，再执行小型真实任务验收。保存脱敏协议样本，不上传应用代码或真实会话。未知版本进行能力探测；不兼容时给出明确状态，不自动套用可能失效的写操作。

版本适配集中在一个模块，核心任务状态与 MCP 接口保持独立。GitHub 的自动测试只验证源代码和模拟场景；登录态和桌面更新必须在本机验收。后续如需定时监测，另行安排。

## 工作量判断

以下是工程估算，不是已经测得的工期：单任务通道 2–5 个工作日；生命周期与端到端测试 3–7 日；安装、Skill 与发布 1–3 日。预计 6–15 个有效开发日，首轮握手和桌面会话注册可能增加时间。

主要难点是内部协议、会话与权限生命周期、应用升级兼容。Intel CPU 本身不需要翻译这些协议；Intel 的额外工作集中在运行时和原生依赖安装。当前依赖中 `cryptography` 在本机曾需要源码编译，应作为安装验收项。
